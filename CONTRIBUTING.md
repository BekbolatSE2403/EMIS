# Contributing to EMIS

Keep report and repository evidence consistent. Use [docs/README.md](docs/README.md) as the documentation index and docs/EMIS_Requirements_Specification.md for canonical IDs. Update linked architecture, data/API/privacy decisions, tests, feedback-response mapping and Word companions together when their meaning changes.

Use a focused branch and reviewed PR. Link actual issue IDs after verifying them; do not infer task completion from branch names. Attribute contributions to their actual authors. Keep secrets and identifying survey/health data out of commits; examples use fictional profiles and sanitized configuration.

For each change distinguish documented target, implemented code, executed test and reviewer approval. Record actual test build/date/conditions. A survey summary, Figma screen, planned endpoint or successful frontend build does not prove integrated security. Initial planning feedback is received; record follow-up review separately with its real date when it occurs.

Use Markdown for editable engineering details and regenerate/review Word snapshots after content changes. Preserve original chart/diagram evidence unless intentionally replaced with clearly labeled current evidence. Never rewrite a historical screenshot or report date to imply testing or approval that did not happen.
